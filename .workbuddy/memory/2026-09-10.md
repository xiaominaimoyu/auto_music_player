# 第四轮：拿到正式调研报告 → 出需求分析与集成计划

## 锁定的键位（推翻我第二轮的推测）
- PC 音位行 **Z X C V B N M = 1 2 3 4 5 6 7**（从左到右上行）
- 鼠标三修饰态（**按住态**）：左键=降调(低八度)／中键(滚轮)=升半音／右键=升调(高八度)
- `,` = 高音1 物理直达；`.` `/` 疑似高音2/3（待确认）
- 点按=单音，**长按=延音、松开收音** → 现有 `hold_ratio` 设计是对的。
  （我第二轮根据视频标题推断"长按=升降、长按不延音"是**错的**，升降靠鼠标修饰键）
- 无和弦、无滑音；明确规则"不要多点"

## 关键代码发现
- **`core/keyboard_driver.py` 里 MOUSEINPUT 与 INPUT 联合体早已定义但从未使用**
  （第 32–59 行）→ 鼠标能力底层已就位，不用推倒重来。
- `core/score_model.py` 的 note_id schema 与 `android/` 端共享 → 半音扩 schema 会波及安卓端，
  故 MVP 建议不动 schema，走 profile 级降级策略。

## 核心结论：不是"换映射"，是"换范式"
现有 = 21 个独立键（3行×7）；三角洲 = 7 音位 × 4 修饰态 + 鼠标。
→ 工作量从第二轮估的 2–3 天上调到 **纯开发 5.5 工作日 / 日历 1.5–2 周**。

## 计划要点
- 新增模块：`core/profile.py`（档位）、`core/compiler.py`（谱→输入事件序列）、
  `core/input_driver.py`（键鼠统一）；改造 keymap/player/keyboard_driver。
- 时序硬约束：修饰键 down → ≥30ms → 音键 down → 按住 → **音键先 up** → 修饰键 up
  （顺序错了最后一个音会被转调）。
- `_release_all()` 必须补鼠标键释放，否则右键卡住会持续顶在高八度。
- 阻塞性待确认 4 项：`.`/`/` 键位、修饰态能否叠加、切出口琴的前置序列、自由演奏与任务是否同管线。
- 风险 R3：腾讯 ACE 反作弊，需用户明确接受。
- 已读模块新增：main.py、core/score_model.py

# 第五轮：用户拍板 → 计划 v2 定稿

用户逐条回复决策与阻塞项，产出计划 **v2（决策定稿）**（同文件覆盖 v1）。

## 用户拍板的决策
1. **D1 半音**：同意不动 schema，但升级为「**schema 冻结、内部 IR 不冻结**」——
   IR 从第一天带 `semitone: 0|1`，持久层 note_id 不写；**降级发生在编译期**（非导入期），
   产出「降级清单」；V2 放开正则后用户无需重导谱。
   论据权重修正：半音"长尾"只在 NPC 任务成立，自由演奏下限未知，不能推全局。
2. **D2 冲突**：做成全覆盖纯函数 `resolve_modifier(state_set, policy) → (state, warnings)`，
   策略枚举 OCTAVE_FIRST / REJECT_NOTE / KEEP_ACCIDENTAL，单测全覆盖。
3. **标点 `,.` `/`**：仅 `,` = 高音1 启用（中高可信）；`.` 低可信（《花海》谱整行错位已证伪）；
   `/` 无证据 → 都不启用。关键结构判断：**标点路径结构上不可能完整**（最多高音1-3，
   右键覆盖1-7）→ **RMB 路径必做**，标点只是优化。R4 如实改为"仅高音1 可规避右键"。
4. **修饰态叠加**：按**四态互斥枚举**（NATURAL/LOWER/SEMITONE/HIGHER）建模，不 bitmask。
   证据：手游三钮并排单选 + 教程全为顺序切换 + 无叠加谱例。
5. **pre-roll 已查明**：口琴是 EDC 工具包专属槽，轮盘默认键 **6**。
   S1 = 按6→等轮盘→选槽位(可配)→等动画(默认800ms)→首音；
   **S2 NPC 任务零 pre-roll**，post-roll = Q 提交。
   **关键会话规则**：S2 被打断后手动重掏**不能提交曲谱**，只能重听 NPC 示范
   → S2 中断语义是 abort（不可续），不是 pause。
6. **双场景分层**：音符层同一不 fork，差异收敛到 `FreePlayScenario` / `NpcQuestScenario`。

- **config 迁移兼容**：老用户 config.yaml 的 keymap 段要保留作 fallback，否则升级即破坏配置。

  让"互斥"成为策略而非类型约束 → 若实测可叠加只改配置。（用户原话不要 bitmask，此为可选折中）

## 我新发现的 3 个坑（v2.1 核心增量）
1. **C5 `profiles/` 打不进 exe**（读 spec 确认）：
   `AutoMusicPlayer.spec:55` `datas=[("config.yaml","."),("app.ico",".")]` 只有两个文件、无目录；
   `main.py::ensure_config()` 也只处理单文件、不拷目录。
   → onefile 下 profiles 会落在 `_MEIPASS` 临时目录，用户改的配置会丢。
   解法：datas 补 `("profiles","profiles")` + 新增 `ensure_profiles()`（存在则不覆盖）。
2. **D8 半音注入通道缺失**：持久层不写 semitone ⇒ MVP 阶段该字段恒为 0 ⇒
   `resolve_modifier` 的 SEMITONE 分支永远不执行，**风险原样后移到 V2**，正是 D1 想避免的。
   解法：`compile(..., semitone_source="none"|"raw_text")` 开关，MVP 默认 none，
   但 **SEMITONE 分支与 low+#/high+# 降级路径 MVP 就要有单测**（手工构造 IR）。
3. **D9 raw_text 与 notes 下标对齐不保证**：`parser.py` 会跳空行/调号行/歌词行、剥小节线，
   raw_text 第 N 字符 ≠ notes 第 N 音符，V2 直接按下标回填会整体错位。
   解法：同版 parser 重放 + `len(replayed)!=len(notes)` 则**拒绝注入**并降级告警。
   推论：parser 行为变更视为破坏性变更，建议入库时存 parser_version（可用新增列，不影响安卓端）。

## 另外 5 项澄清
