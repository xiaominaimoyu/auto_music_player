## 1. 问题一：更新后旧版乐谱是否保留

### 1.1 现状机制（已核实）

**数据目录解析**（`main.py:180` `_resolve_data_dir`）：

- `data_mode: portable` 或未打包运行 → 使用 `config.yaml` 同级的 `data/`
- `data_mode: auto` 且 exe 旁存在 `data/` 或 `portable.flag` → 沿用便携目录
- 其余情况（安装版）→ `%LOCALAPPDATA%\AutoMusicPlayer\data`（`core/app_identity.py:92` `stable_app_root`）
- MSIX 包身份 → `LocalState\data`，并先走 `core/data_migration.py` 的一次性合并（只复制、不删除、冲突文件改名为 `*.legacy-<时间戳>`、成功后写 marker）

**曲库本体**（`core/database.py`）：

- `SCHEMA_VERSION = 2`，记录在 SQLite `PRAGMA user_version`
- 构造时若 `user_version < SCHEMA_VERSION` 且文件非空，先 `backup_to()` 出 `scores.db.pre-v2.<时间戳>.bak`，再建表
- 表结构全部 `CREATE TABLE IF NOT EXISTS`，只增不改
- 来源附件按 SHA-256 存到 `data/sources/<sha256>.<ext>`，DB 里存相对路径

**结论**：曲库跟着 `data/` 目录走，程序本体（EXE）替换不影响它。只要不覆盖 `data/`，乐谱、来源附件、曲目偏好都在。

### 1.2 真实风险点

| 编号 | 风险 | 触发条件 | 后果 |
|---|---|---|---|
| R1 | 用户解压整个 zip 覆盖 | 发布包内含 `config.yaml` 与空 `data/` 结构 | 旧 `scores.db` 被冲掉或程序指向新空目录 |
| R2 | `data_mode` 变更 | 便携版与安装版之间切换 | 旧库还在，但程序看不见，表现为"乐谱全没了" |
| R3 | 未来 schema 升级无门禁 | `update_checker` 解析了 `db_schema_version`、`min_supported` 却从未消费 | 老客户端下载新程序，启动才发现版本过高 |
| R4 | 迁移备份对用户不可见 | 备份是静默行为 | 出问题时用户不知道备份在哪 |

### 1.3 已有方案：曲库找回

`core/library_recovery.py` `recover_library(db, old_path)` 已经实现，并由 `gui/library_tab.py` 的"找回旧曲库"按钮调用：

1. 以 `mode=ro` + `trusted_schema=OFF` 只读打开旧库，绝不写回
2. 校验 `user_version` 不高于当前程序版本；没有 `scores` 表直接拒绝
3. 导入前用 SQLite backup API 给当前库留一份 `.pre-recovery.<时间戳>.bak`
4. 逐首按内容指纹去重（`recovered_scores` 表），重试幂等
5. 附件必须落在旧库的 `sources/` 内（拒绝路径穿越）、SHA-256 必须与记录一致、≤500 MB
6. 任一失败整体回滚，并清掉本次新建的附件

测试：`tests/test_library_recovery.py`（含 GUI 确认流程与重试）。

## 2. 问题二：程序内自动下载更新

### 2.1 现状机制（已核实）

`core/update_checker.py` 已具备：

- Ed25519 验签，签名对象是 canonical JSON（`sort_keys` + 紧凑分隔符），公钥硬编码为 `RELEASE_PUBLIC_KEY`，配置里的 `public_key` 不参与信任
- 多镜像（GitHub / Gitee）逐个校验，取 `(sequence, version)` 最大的有效清单；单个镜像失败不影响另一个
- 拒绝回滚：`sequence` 低于当前或版本低于当前都判失败
- `issued_at` 不得晚于当前时间、`expires_at` 过期即拒
- 强制 HTTPS，重定向到非 HTTPS 直接抛 `UpdateSecurityError`
- 清单 ≤1 MB，更新包 ≤2 GB
- 下载：临时 `.part` 文件 → 边下边算 SHA-256 → 大小与哈希都匹配才 `os.rename` 发布 → **绝不覆盖同名文件**
- 支持取消（`UpdateCancelled`）与进度回调

`gui/main_window.py` 已接线：`_check_updates` → `_start_update_job`（`QThread` + `QProgressDialog`）→ `_offer_download` → `_download_finished`。Store 通道改为提示走 Microsoft Store。

### 2.2 必须立刻处理：清单落后

| 项 | 当前值 | 位置 |
|---|---|---|
| 程序版本 | 1.5.1 / sequence 151 | `core/version.py` |
| 发布清单 | 1.5.0 / sequence 150 | `updates/stable.json` |

后果：用户点"检查更新"，两个镜像都命中 `manifest.sequence < current_sequence` 而被拒，走完循环后返回错误串——用户看到"检查更新失败"，而不是"已是最新"。

### 2.3 自替换为什么没做

`docs/发布签名与更新器门禁.md` 明确划了线：没有正式 Authenticode 证书、没有回滚测试证据之前，保持第一阶段（只下载并提示手动替换）。当前本机有 `signtool.exe`，但没有可正式发布的证书。

## 3. 实施步骤

### 3.1 旧曲库安全（对应 R1–R4）

**P0-1 启动时探测旧库，交由用户确认**

- 位置：`main.py` 创建 `ScoreDB` 之前
- 逻辑：目标 `scores.db` 不存在，但另一侧（exe 旁 / `%LOCALAPPDATA%`）存在旧库里 → 弹一次"发现旧曲库"，用户确认后调用现有 `recover_library()`
- 约束：不自动改 `config.yaml`、不自动迁移、原库只读
- 验收：便携版放一个旧 `scores.db` 到 LocalAppData 侧，启动即被发现；拒绝后原库字节不变

**P0-2 发布门禁消费 `db_schema_version`**

- 位置：`core/update_checker.py` `download_update()`，在联网之前
- 逻辑：`manifest.db_schema_version > ScoreDB.SCHEMA_VERSION` → 抛错，提示"请从发布页手动更新"
- 同时 `_offer_download` 在 `min_supported` 不满足时给出明确警告
- 验收：构造一个 `db_schema_version=99` 的签名清单，下载被拒且未发起任何网络请求

**P1 迁移备份对用户可见**

- 首次启动若发生过 schema 迁移，状态栏提示"已自动备份到 <路径>"
- 验收：从 v1 库启动一次，状态栏出现备份路径且文件存在

**P2 迁移演练脚本**

- `tools/` 下新增脚本：拿旧版 `scores.db` 跑一次 v2 迁移 + 找回，供发布前自测

### 3.2 自动更新

**P0-3 版本三处同步，缺一拒发**

- `version.txt` → `core/version.py`（`APP_VERSION` / `UPDATE_SEQUENCE`）→ `updates/stable.json`（`version` / `sequence` / `size` / `sha256`）
- 实现建议：发布脚本里比对三者，任何一处不一致就终止打包；`AutoMusicPlayer.spec` 加断言
- 验收：故意只改 `version.txt`，构建失败并指出缺哪一处

**P0-4 清单重签**

- 用 `tools/update_manifest.py sign` 重签 `updates/stable.json`，私钥不进仓库
- 验收：`tools/update_manifest.py verify` 通过；客户端"检查更新"显示"当前已是最新版本"

**P1 自替换（第二阶段，需拍板）**

- PyInstaller 单文件 EXE 运行中无法覆盖自身，需要退出后由外部 helper 替换
- 流程：备份 `data/` 清单 → 原子替换 EXE → 失败回滚旧 EXE → 自动重启
- 前置：正式签名证书 + 至少一个版本完成干净机验收 + 自动化回滚测试
- 不做这条，用户仍要手动替换文件
