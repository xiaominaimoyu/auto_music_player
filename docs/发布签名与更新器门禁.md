# 发布签名与更新器门禁

## 当前状态

AutoMusic Player 的应用内更新 manifest 使用 Ed25519 签名；公钥只进入 `config.yaml`，私钥保存在发布机的用户密钥目录，不进入仓库、安装包或日志。第一阶段更新器只检查镜像、验证签名/版本/哈希并提示用户，不下载、不替换程序。

当前工作区已提供 `tools/sign_windows_release.ps1`。本机检查到 Windows SDK 的 `signtool.exe`，但没有可用于正式发布的、带私钥且链到受信任根的 Authenticode 证书。因此当前不能声称 EXE 已完成可信签名，也不应使用自签证书绕过发布门禁。

## 正式分发选择

如果目标是面向普通 Windows 用户的正式安装版，优先考虑把应用打成 MSIX 提交 Microsoft Store。通过审核后，Store 会为 MSIX 重新签名并负责 Store 更新；这条路径不要求本项目购买 CA Authenticode 证书。注意：仅把现有 EXE/MSI 的下载链接提交到 Store，不享受这项代签名和 Store 更新能力，EXE/MSI 仍必须由发布方自行签名。

GitHub/Gitee 便携版仍应保留独立的可信签名门禁；Store 版和便携版可以共存，但不能让 Store 版继续执行自有 EXE 替换更新。按需下载的 Audiveris/jpeditor 组件也不因 Store 签名而免除来源、SHA-256、许可证和人工确认检查。

## 正式证书要求（GitHub/Gitee 便携版）

正式发布前由发布方选择可信 CA 的 OV/EV Authenticode 证书，或组织可审计的 Azure Trusted Signing 身份。证书必须具备：

- 代码签名增强型密钥用法、未过期、带私钥；
- Windows 信任链可验证，发布机能访问撤销检查；
- RFC 3161 时间戳服务地址；
- 私钥由证书提供方或组织密钥存储保护，不提交到 Git。

Audiveris 的上游 MSI 和展开目录中的部分第三方 PE 是否签名，不改变本项目自身签名门禁；发布时只对 AutoMusicPlayer 自有 EXE/更新器签名，并在第三方来源、版本、SHA-256 和许可证记录中保持可追溯。

## 签名命令与验收

将正式证书安装到发布机证书存储后，以证书指纹运行：

```powershell
.\tools\sign_windows_release.ps1 `
  -FilePath .\dist\AutoMusicPlayer.exe `
  -CertificateThumbprint '<40 位证书指纹>' `
  -TimestampUrl 'https://<CA 提供的 RFC3161 时间戳地址>' `
  -Description 'Auto Music Player'
```

脚本会使用 SHA-256 签名、验证 `/pa /all`、检查 `Get-AuthenticodeSignature` 为 `Valid`，并打印最终文件 SHA-256、签名者和时间戳。上传 GitHub/Gitee Release 前还要在一台干净 Windows 机器上复核签名链、下载文件大小和 SHA-256。

## 更新器分阶段门禁

第二阶段“自动下载并替换”只有在以下条件全部满足后才实施：

1. 正式证书已签发，至少一个正式版本完成签名、时间戳和干净机验收；
2. GitHub/Gitee 两个 manifest 镜像连续运行一个发布周期，均能验证并回退到另一镜像；
3. 更新器 helper 本身也签名，下载使用临时文件，先校验大小、SHA-256、版本和 Authenticode，再原子替换；
4. 更新前完成数据库/配置/用户乐谱备份，迁移失败能恢复旧版本和旧数据；
5. 对下载中断、磁盘不足、程序锁定、镜像失效、签名失效、迁移异常和重启失败完成自动化回滚测试，并保留用户明确同意开关。

在证书和上述回滚证据缺失时保持第一阶段提示模式。建议在首个可信签名版本发布并观察 1--2 周、至少完成一次旧数据迁移演练后，再排期第二阶段；若期间出现签名链或镜像问题，继续延后而不是静默自动替换。
