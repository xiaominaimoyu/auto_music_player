## 0. 结论先行

调研把键位锁死了，但**输入模型与现有架构不是"换映射"的关系，而是"换范式"**：

| 维度 | 现有模型（鸣潮/原神） | 三角洲模型 | 性质 |
|---|---|---|---|
| 音高寻址 | **21 个独立键**（高/中/低 3 行 × 7） | **7 个音位键 × 4 种修饰态** | 范式冲突 |
| 输入设备 | 仅键盘 | **键盘 + 鼠标左/中/右三键** | 能力缺失 |
| 时值控制 | `hold_ratio` 比例按住 | 按住时长决定，松开收音 | ✅ 天然兼容 |
| 和弦 | 支持（多键同响） | 不支持，倾向单音/后按覆盖 | 需降级 |
| 半音 | 无此维度 | 中键升半音 | IR 需支持 |
| 前置动作 | 无 | 口琴由用户手动从背包启用，程序不做自动切换 | 无需新增 |

**范围（v2 锁定）**
- 仅 **PC 端**，交付形态为 **exe**（复用现有 `AutoMusicPlayer.spec`）
- 鸣潮/原神 **原样保留**，与三角洲在**不同 profile 分区**（`profiles/default.yaml` vs `profiles/delta_force_harmonica.yaml`），GUI 档位下拉按分区分组
- 手游端不在本计划（V3）

**工作量**：纯开发 **5.5 个工作日**；日历 **1.5–2 周**（M0 实测阻塞可并行消化）。

**两个好消息**
1. `core/keyboard_driver.py` 里 **`MOUSEINPUT` 与 INPUT 联合体早已定义，只是从未使用**（第 32–59 行）——鼠标能力底层已就位。
2. `scores` 表**已有 `raw_text` 字段**（`core/database.py` 第 28 行）——D1 要求的"原始谱面文本原样留存"是**现成的，零成本**，不需要动数据库。

## 1. 需求映射：调研结论 → 能力缺口 → 改动点

### 1.1 按键映射（《调研》§1）

**锁定事实（可信度高）**
- PC 音位行：**Z X C V B N M = 1 2 3 4 5 6 7**，从左到右严格上行
- 鼠标三修饰态（**按住态 latch-while-held**）：左键=降调（低八度）／中键（滚轮按下）=升半音／右键=升调（高八度）
- 手游：1–7 数字格 + 三个**并排**状态钮，与 PC 同构

**缺口与改动**
1. `core/keymap.py` 的 `KeyMap` 强校验「3 段 × 7 键」，`key_for()` 返回单个按键字符串 → 泛化为返回「修饰态 + 主键」组合。
2. `config.yaml` 只有一份全局 keymap，**无游戏档位概念** → 引入 profile 分区。

### 1.2 出声机制（《调研》§2）

- 点按 = 一个单音；**长按 = 延音，松开即收音，时长 = 按压时长**（→ 现有 `hold_ratio` 设计正确，无需改）
- 明确规则「未标注均单点一下即可，**无论有无声音不要多点**」→ 多点会多生成音符
- 拖动/滑音/和弦无证据，倾向不支持

**缺口与改动**
3. `core/keyboard_driver.py` **只有键盘能力** → 增加鼠标三键 press/release。
4. `Player._run` 的 `press_chord(keys)` 假设"多键 = 和弦" → 对三角洲必须**禁止多键同按**，改为策略化降级。
5. `_release_all()` **只释放键盘** → 必须补鼠标键释放，否则右键卡住会持续把音顶在高八度。

### 1.3 音区切换（《调研》§3）

- 不是八度键/翻页/吹吸配合，而是**修饰键按住态**
- 不松开则后续每个音都被转调，必须显式"松手"才回自然音

**缺口与改动**
6. `core/player.py` 需增加**修饰态生命周期管理**：进入音符前按下修饰 → 按主键 → 按住时值 → **先松主键** → 再松修饰。顺序错了最后一个音会被转调。

### 1.4 排列规则与按住差异（《调研》§4）

- 底排向左无键 → **低音没有物理直达键，只能按住左键**
- 音键长按不影响后续音；**鼠标修饰键影响后续所有音** → 释放时机是正确性问题，不是手感问题

## 2. 目标用户与使用场景

### 2.1 场景总览

| 场景 | 描述 | 优先级 |
|---|---|---|
| **S1 局内自由演奏** | 用户手动从背包启用口琴后，选谱自动吹奏 | P0 |
| **S2 NPC 听旋律复刻任务** | 「风声未止」按提示复刻，**只校验音高序列与长音位置，不卡节奏** | P0（最高性价比） |
| S3 谱面试听校对 | 不进游戏，用记事本/预览面板验证编译结果 | P1 |
| S4 手游端 | 屏幕坐标管线 | P2（本计划不含） |

### 2.2 音符层 vs 会话层（v2 关键分层）

《调研》与用户复核确认：**音符层同一，会话层不同**。

| 差异维度 | S1 自由演奏 | S2 NPC 任务 |
|---|---|---|
| 进入方式 | **用户手动从背包启用** | NPC 示范后**自动装备** |
| 退出 | 手动收起 | **`Q` 提交**判定 |
| 校验 | 无 | 只认音序 + 长音位置，不卡节奏；「不要多点」 |
| 中断恢复 | 随时可再掏，**可续播** | **再掏即丧失提交资格** → 必须 abort + 重开 NPC 对话 |
| 自动演奏按钮 | 可见 | 不可见 |

> **架构结论**：`NoteCompiler → InputEvent` **只做一套，音符层不 fork**；会话层差异收敛到两个 `ScenarioAdapter`（见 §6.3）。

## 5. 关键设计决策（已定稿）

### D1 ✅ 定稿：**schema 冻结、内部 IR 不冻结**

| 层 | 处理 |
|---|---|
| 持久层 `note_id` | **不动**正则 `^(high\|mid\|low)_([1-7])$`，不逼安卓端同步 |
| 编译器内部 IR | **第一天就带 `semitone: 0\|1`** |
| 降级时机 | **编译期**，不是导入期 |
| 原始谱面 | `scores.raw_text` **原样保留**（字段现成，零成本） |
| 产物 | **降级清单**：第 N 音 / 请求态 / 实际态 / 原因 |

**收益**：V2 放开正则后**用户不需要重新导谱**。共享 schema 冻结的是**入库格式**，不应连带冻结中间表示——否则 V2 要同时改 schema + 编译器 + Player 三层。

> **论据权重修正（v2）**：v1 我写"半音是长尾"，这个论据**只在 NPC 任务场景成立**（6 首隐藏谱仅佐拉段用到，且自然音 354 版本通过更多）。自由演奏场景的下限未知，不能据此推断为全局长尾。半音能力从第一天进 IR 的决策因此更有必要。

### D2 ✅ 定稿：**OCTAVE_FIRST，做成全覆盖纯函数策略**

```python
def resolve_modifier(state_set, policy) -> (single_state, warnings)
```

| 请求组合 | OCTAVE_FIRST（默认） |
|---|---|
| `low + #` | 取 low 自然音 + 告警 |
| `high + #` | 取 high 自然音 + 告警 |
| `low + high` | 回自然音 + 告警（可配置为 REJECT_NOTE 拒绝该音） |
| 任意冲突 | 告警事件进事件流，GUI 汇总计数 |

策略枚举：`OCTAVE_FIRST` / `REJECT_NOTE` / `KEEP_ACCIDENTAL`。**单测全覆盖**（含全部组合 × 全部策略）。

**判据**：八度错 = 整句跑偏；半音错 = 味道不对。

### D3 ✅ 定稿：**标点直达只启用 `,`，`.` `/` 不启用**

| 键 | 结论 | 处置 |
|---|---|---|
| `,` = 高音 1 | **中高可信**（界面第 8 格为高音 ī；红凯谱原文"M 旁右边的逗号那个键"） | ✅ 启用 |
| `.` = 高音 2 | **低可信**（唯一来源《花海》谱，其整行映射已被证伪——跳过 4、整体错位一格） | ❌ 注释掉，标"待 P1-3 自检" |
| `/` = 高音 3 | **无证据** | ❌ 注释掉 |

**关键结构判断**：标点路径**结构上永远不可能完整**——即使 `,./` 全部成立也只覆盖高音 1–3，而右键覆盖高音 1–7。因此：
- **RMB 路径是必做的**，标点路径只是"高音 do 少一次修饰切换"的优化
- profile 中标点直达做成**可选覆盖表**（`pitch_direct_overrides`），只填 `,→high_1`
- **R4 修正**：不存在"仅用 `,.` 物理键"的右键规避方案，正确表述是「**仅高音 1 可规避右键**」

> 强信号：翻遍所有 PC 谱（含大量用高音的《死别》《欧布小曲》），**没有任何一份真的用 `.` `/` 键，全部走右键 + 音键**。要么路径不存在/不完整，要么玩家普遍不知道。

### D4 ✅ 定稿：**四态互斥枚举，不做 bitmask**

**证据（三方一致，倾向互斥）**
1. 手游界面「降调 / 半音 / 升调」是**三个并排状态钮（单选形态）**
2. 所有教程均为「按住左键 → 松手 → 再按中键」的**顺序切换**
3. **从未出现两态同按的谱例**

**建模**：`NATURAL / LOWER / SEMITONE / HIGHER` 四态枚举。互斥模型下，冲突在类型层就很难构造出来——这对 D2 也是最省事的。

**兜底**：M0 实测脚本保留一项「按住左键 + 中键敲 Z，听是低音 / 低音# / 没声」，1 分钟出结果。若实测可叠加，只改 `resolve_modifier` 一个函数。

> 💡 **可选项（建议你拍板）**：把 IR 里的修饰态存成 `frozenset` 而非枚举，但 profile 声明 `modifier_mode: exclusive`，由 `resolve_modifier` 在 exclusive 模式下收敛到单元素。这样"互斥"是**策略**而非**类型约束**——若实测可叠加，改配置即可，代码零改动。实现成本与纯枚举几乎相同。**不做也是完全合理的**，纯枚举更简单。

### D5 ✅ 定稿（v2.1 → v2.2 修订）：**移除自动 pre-roll，口琴由用户手动启用**

> **修订说明（2026-09-10，应用户要求）**：原计划"程序按 `6` 唤出 EDC 轮盘自动选口琴"
> **已移除**。理由：① pre-roll 是**盲发无反馈**，打空/打错无法检测；② EDC 槽位由用户装配
> 决定，自动序列无法写死；③ 让用户先手动启用，把"是否就绪"的判断权交回给人，最稳最简单。

**入口背景**：口琴是 **EDC 工具包专属槽**物品，也可从背包直接启用。

| 场景 | 口琴如何就位 | 程序行为 |
|---|---|---|
| S1 自由演奏 | **用户手动从背包/EDC 启用口琴**后再点开始 | **无任何 pre-roll**；倒计时结束直接弹第一个音 |
| S2 NPC 任务 | NPC 示范后**自动装备** | 无 pre-roll；post-roll 为 **`Q` 提交** |

**用户流程（S1）**：手动启用口琴 → 本工具选档位+乐谱 → 点开始 → 倒计时内切回游戏窗口 → 程序直接演奏。

**S2 会话规则（不变，重要）**：中途被打断、口琴被切下后，**手动重新掏出来不能提交曲谱，只能重新听 NPC 示范**。因此 S2 的中断策略是 **abort 本轮 + 提示重开 NPC 对话**（UC-9）。

### D6 ✅ 定稿：**一层编译器 + 两个 ScenarioAdapter**

```
                    ┌─ FreePlayScenario ─┐
NoteCompiler ─→ InputEvent[]             ├─→ Player
                    └─ NpcQuestScenario ─┘
```

| Adapter | 口琴就位 | submit | 中断语义 | 音符间隔 |
|---|---|---|---|---|
| `FreePlayScenario` | **用户手动启用**（无自动 pre-roll） | 无 | `pause`（可续播） | 按音乐时值 |
| `NpcQuestScenario` | NPC 示范后自动装备（无 pre-roll） | `Q` | `abort`（不可续，提示重来） | 按"识别友好"调——**宁可慢、不可叠键** |

### D7 ✅ 关闭：**「挽歌」表情动作排除**

S10 宣传里的干员「挽歌」吹口琴是**表情动作**，与 EDC「守夜人口琴」不是一回事。**本计划目标不含该动作**，只做乐器口琴的弹奏功能。无需再查证其键位。

### D8 ✅ 定稿（v2.1 新增）：**半音注入通道 —— 防止 IR 字段变成摆设**

**问题**：D1 定了"IR 带 `semitone`、持久层不写"。但持久层不写 ⇒ MVP 阶段 `semitone` **恒为 0** ⇒ 这个字段在运行时永远走不到，`resolve_modifier` 的 SEMITONE 分支也永远不执行。**等于把风险原样后移到 V2**——V2 时才第一次接通，届时"改 schema + 改解析 + 改编译"三层又要一起动，正是 D1 想避免的局面。

**解法：MVP 就把注入通道做出来，只是默认关闭。**

```python
compile(notes, bpm, *, raw_text=None, semitone_source="none" | "raw_text")
```

| 阶段 | `semitone_source` | 行为 |
|---|---|---|
| MVP | `"none"`（默认） | 全序列 `semitone=0`，不读 `raw_text` |
| V2 | `"raw_text"` | 从 `raw_text` 重解析 `#` 记号，按 index 回填 |

**硬性要求**：`resolve_modifier` 的 `SEMITONE` 分支与 `low+#` / `high+#` 两条降级路径，**MVP 就要有单测**（用手工构造的 IR，而非依赖运行时走到）。这样 V2 只是"打开开关 + 放开正则"，架构零改动。

### D9 ✅ 定稿（v2.1 新增）：**raw_text 与 notes 的下标对齐不保证，必须校验**

**问题**：D1 依赖"从 `raw_text` 重新解析出半音"，但 `core/parser.py` 会跳过空行、调号行（`1=C`）、歌词行，并剥掉小节线——**`raw_text` 的第 N 个字符 ≠ `notes` 的第 N 个音符**。若 V2 直接按下标回填 semitone，会整体错位。

**解法（两条约束）**
1. **同版解析器重放**：V2 注入时用**与入库时同一版本**的 `parser` 重解析 `raw_text`，得到重放序列；因解析确定性，重放序列与 `notes` 应同构。
2. **长度一致性校验**：`len(replayed) != len(notes)` → **拒绝半音注入**，降级为全 `semitone=0` 并告警，绝不静默错位回填。

> 推论：`parser` 的行为变更需视为**破坏性变更**。建议在 `raw_text` 入库时同时存一个轻量 `parser_version` 标记（**仍不改 `notes_json` schema**，可用现有 `source_type` 字段或新增独立列——新增列属加字段，不影响安卓端读取）。

### 6.2 核心数据结构（概念示意）

```
# 内部 IR（v2 起就带 semitone）
IRNote:   { pitch: 1-7, octave: -1|0|+1, semitone: 0|1, dur_beats: float }

# 修饰态（互斥枚举，D4）
Modifier: NATURAL | LOWER | SEMITONE | HIGHER

# 解析结果
KeyCombo: { modifier: Modifier, key: "Z" }

# 事件流
InputEvent: { t_ms, device: "kb"|"mouse", key, action: "down"|"up" }

# 降级清单
Degradation: { index, requested: "low+#", actual: "low", reason: "OCTAVE_FIRST" }
```

### 6.3 单音符时序规范（正确性硬约束）

```
[修饰键 down] ─≥ modifier_settle_ms─→ [音键 down] ─hold_ms─→ [音键 up] ─≥ modifier_hold_ms─→ [修饰键 up]
```

- `modifier_settle_ms`：默认 **30ms**，可配——太短游戏可能没注册修饰态
- **音键必须先于修饰键释放**，否则最后一个音被继续转调
- `max_hold_ms`：默认 **3000ms**（《调研》长音约 2–3 秒）
- `modifier_hold_ms`：默认 20ms，可配

### 6.4 中断语义（v2 新增）

现有 `Player` 只有一种停止语义（`paused` 信号 + 可续播）。S2 需要**不可恢复中止**：

| 语义 | 触发 | 行为 | 场景 |
|---|---|---|---|
| `pause()` | F8 / 失焦 | 释放所有键鼠，进度经 `paused` 带出，**可续播** | S1 |
| `abort(reason)` | S2 失焦/打断 | 释放所有键鼠，**清空进度**，发 `aborted(reason)`，GUI 提示重开 NPC 对话 | S2 |

### 6.5 策略枚举汇总（C7 补齐）

**所有降级/冲突决策一律参数化，不允许散落在业务代码里。**

| 函数 | 策略枚举 | 默认 |
|---|---|---|
| `resolve_modifier(state_set, policy)` | `OCTAVE_FIRST` / `REJECT_NOTE` / `KEEP_ACCIDENTAL` | `OCTAVE_FIRST` |
| `resolve_chord(notes, policy)` | `CHORD_FIRST`（取首音）/ `CHORD_REJECT`（拒绝该音）/ `CHORD_ARPEGGIATE`（拆成琶音） | `CHORD_FIRST` |

> **C6 澄清**：在 D4 的互斥枚举模型下，`octave` 是单值 `-1|0|+1`，因此 **`low + high` 在类型层不可构造**。D2 表中该行是为 V2 若放开 bitmask 而保留的用例——**MVP 实现时保留其单测，但运行时不可能触发**（单测需手工绕过类型构造，或直接测 `resolve_modifier` 函数本身）。实现者不必为它在 MVP 里找触发路径。

### 6.6 口琴启用语义（C8 已关闭 —— D5 v2.2 修订）

**自动 pre-roll（程序按 `6` 唤出 EDC 轮盘）已移除，口琴由用户手动从背包启用。**

原 C8 的问题是：pre-roll 是**盲发无反馈**（不与游戏交互），打空/打错无法检测。
既然判断"是否就绪"无法自动化，就把它**交回给用户**——最稳、最简单。

| 约定 | 内容 |
|---|---|
| 性质 | 程序**不做任何**自动切换动作 |
| 用户责任 | S1 开始前**手动从背包/EDC 启用口琴** |
| UI 责任 | 开始按钮旁提示：「请先手动把口琴拿在手里，再点开始演奏」 |

### 7.1 ✅ 已解决：`profiles/` 打不进 exe（C5 新发现）

**原问题**
- `AutoMusicPlayer.spec` 第 55 行原为 `datas=[("config.yaml", "."), ("app.ico", ".")]` —— **只有两个文件，没有目录**
- `main.py::ensure_config()`：只处理 `config.yaml` 单文件从 `_MEIPASS` 释放到 exe 旁，**不处理目录**
- 后果：onefile exe 下 `profiles/` 若只走 `datas`，会落在 `_MEIPASS` 临时目录（退出即清理）→ 用户改过的档位配置会丢

**已实施的解法（M3 完成）**
1. ✅ `datas` 增加 `("profiles", "profiles")`，把目录整体打进去
2. ✅ 新增 `core/profile.py::ensure_profiles()`，仿照 `ensure_config()`：exe 旁 `profiles/` 不存在时才从 `_MEIPASS/profiles/` 释放；**已存在则不覆盖**（保留用户修改）
3. ✅ `main.py` 在 `ensure_config()` 之后调用 `ensure_profiles(".")`

详见 `docs/M3-档位分区规格.md`。
