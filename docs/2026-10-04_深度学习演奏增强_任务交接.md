## 用户已作出的硬性决策

- 本轮只研究深度学习增强演奏表现力；暂不处理 Android，也没有 Android 实机验收条件。
- 不使用外部大模型 API；数据处理和识别保持本地/离线。
- PianoCoRe-A/A* refined 是主训练方向；ATEPP、Vienna 4x22 可作为补充/独立验证域。正式加入前要重新核对许可、格式、去重和 split。
- 接受真人 A/B 偏好数据。真人采集必须主动同意，应用不自动上传；回收只选定 completed JSONL，不能收集 pending、rejected、日志、数据库或整个应用数据目录。
- 当前模型没有达到播放器接入门槛。任何接入都必须先通过数值评估、作品级 bootstrap、盲听/真人 A/B、编译器/游戏表达能力检查，并保留规则回退。
- 目前不做正式训练；可以做 CPU 单元测试和小型梯度 smoke，但不要自行启动全量训练。
- 图片/文档识别、Audiveris、人工确认入库、MIDI 富来源 sidecar、持久化/更新器属于项目总体方案，不是本轮模型接入授权范围。

## 架构和当前数据流

桌面端是 Windows Python/PyQt6 项目，已有解析、MIDI、IR/编译、播放和持久化。必须继续保留遗留 Player 与 Delta EventPlayer 两条播放路径；研究训练代码不应直接改写游戏输入链路。

深度学习链路：

~~~text
PianoCoRe refined score/performance/alignment
        ↓
training/pianocore_dataset.py
ragged NPZ + manifest + train-only normalizer + QC
        ↓
training/sequence_expression.py / train_expression.py
note/chord 特征、timing/duration/velocity/pedal 标签
        ↓
train_sequence_expression.py / audit_sequence_expression.py
序列 pilot、真实秒域/小节指标、候选 shadow
        ↓
规则回退、编译器表达能力和真人 A/B 门禁
        ↓
~~~

training/sequence_expression.py 当前仍是 note/chord 输出模型；历史 make_windows() 固定 core_size=128、context_size=16。已有 score_ioi_seconds 和旧累计 IOI loss，但没有真正按小节规划窗口，也没有 tempo/local 辅助 loss。training/bar_supervision.py 能从纯乐谱几何生成 BarSpans，目前只是诊断层。

## 暂停的下一项：真实小节窗口与 tempo/local 辅助监督

截至本文创建时，training/bar_windows.py、training/bar_objective.py 尚未创建，sequence_expression.py 和 train_sequence_expression.py 也没有这部分接入。

### 窗口布局目标

- 只从 score geometry 生成 1/4/16 小节 span；不能读取 performance target、native target mask 或 start trust。
- 最大输入 512 chord；这是当前均衡 validation 的覆盖证据，不是可随意提高的默认值。
- 每个 chord 只属于一个 core 输出区；context/halo 可以重叠，但不能产生第二次 core loss。
- span 必须在同一窗口完整存在才可辅助监督；超过 512、缺端点、partial bar、跨作品/split 或映射不连续的 span 必须排除并报告，不能截断冒充完整。
- padding、halo、无标签 score-only 上下文不能进 core 或辅助 loss。
- 推理使用和训练相同的 bar policy，即使辅助 loss 关闭也不能退回固定 128。

候选接口（代码尚未落地）：

~~~python
plan_bar_windows(chord_count, boundary_indices, spans, context_size, max_window_chords=512) -> list[SequenceWindow]
~~~

SequenceSample 预计增加 score-only 的 bar_spans、bar_boundary_indices 和必要几何；这些字段必须能由 audit NPZ 重建，不能依赖 target。

### tempo/local 分解

对有效 span，以 score IOI 秒数 s_i、模型预测 log IOI ratio r_i 计算：

~~~text
b = log(sum(s_i * exp(r_i)) / sum(s_i))
local_i = r_i - b
~~~

实现要求：

- 1/4/16 horizon 各自统计，再按 active horizon 等权。
- elapsed loss 比较 sum(s_i * exp(r_i)) 与目标 elapsed；目标 elapsed 使用 clamp_min(minimum_elapsed_s)；第 0 个 score IOI 不能成为有效间隔。
- tempo loss 监督 b，local loss 监督 r_i-b，梯度必须回到 chord log IOI 输出。
- native IOI mask、target mask、start trust 只用于过滤可监督行；不能用于窗口布局。
- 非 finite、负/零间隔、非法 span、padding、跨窗口行应拒绝或 mask，并记录各 horizon valid/excluded/clip 计数。

候选接口（代码尚未落地）：

~~~python
true_bar_objective(prediction_log_ratio, target_log_ratio, score_ioi_seconds,
                   span_rows, span_mask, *, horizons=(1, 4, 16),
                   log_ratio_clip=4.0, minimum_elapsed_s=1e-6,
                   bar_ioi_mask=None) -> (loss_dict, metrics)
~~~

必须保留旧 cumulative_weight 兼容性。新权重建议独立配置 bar_elapsed_weight、tempo_weight、local_weight，默认关闭，先做 CPU synthetic gradient 和小 pilot。

## 实现风险

1. 标签泄漏：规划读取 chord_masks、chord_trusted 或 target 会使验证失真。
2. 推理不可复现：audit NPZ 若不保存 bar geometry，benchmark 会退回固定窗口。
3. 重复监督：halo 不得进 core；同一 chord/span 不得因重叠窗口重复计 loss。
4. off-by-one：bar span 的间隔是 start+1 到 end；第一个 chord 的 IOI 为 0。必须测单小节、partial、正好 512、超过 512 和 horizon 端点。
5. 不完整跨度：partial、缺端点、fold/split/absorb 或非连续 whole-native-chord 不能监督。
6. 旧路径回归：cumulative_weight、fixed 128、predict_sample() 和现有 sequence tests 必须兼容。
7. target-shuffle 只能作负对照；启用 bar loss 时要禁止不安全的组合，或同步置换所有对齐监督字段。
8. 512 chord 只表示 score coverage，不代表游戏仍能保持钢琴声部；仍须经过 MIDI 60 ms prepare_score、重叠/最短 IOI/16 拍约束和映射诊断。

1. **onset 已经封顶，别再碰。** 完美模型最多与观测标签相关 0.652、只解释 42.5% 方差；模型现在 586.04 ms 是相对下限 473.67 ms 的 1.237 倍，同时比"预测 0"还差 1.3%。也就是说这个通道剩下的空间既小、又不可用于任何接入主张。上一节"撤掉 onset 不释放容量、训了也不敌常数"与本轮天花板互相印证。
2. **log IOI 也基本到底**：1.138 倍，比预测 0 只好 2.6%，而跨演奏相关 0.542 说明它比 onset 稳得多（ρ=0.703），剩下的空间主要在模型侧而非标签侧，但绝对量很小。

## 2026-10-11 duration 专项：每曲居中已试过，负向

按上一节的结论把预算转注 `log_key_duration_ratio`，拆成两个独立问题分别测量，两个新工具都是只读或只训练研究臂：`tools/audit_piece_offset_reproducibility.py`（用单向 ICC(1) 检验"每次录音的标签水平"在同一作品不同演奏者之间是否一致，ICC≈1 才是谱面属性、才可能被只看谱面的模型学到）与 `tools/analyze_target_error_decomposition.py`（拿既有 checkpoint 走 `predict_sample` 真实推理路径，把误差按录音拆成水平项与形状项，并给出两侧各自居中的对称口径 `shape_mae`，基线是"每录音预测一个常数"）。

## 2026-10-11 粒度修正：duration 的剩余空间是 0.08–0.10 MAE，不是三分之一

三条直白的结论，请以后不要绕过：

1. **没有任何通道通过数值门槛**，而且两条是"显著更差"：duration 比每条录音的常数基线差（P(model worse)=1.000），onset 比"完全不增强的原谱"差（P=0.976）。也就是说当前模型若接进播放器，最可能出现的可测后果是**比不增强更难听**。
2. **行加权会高估成果**：同一批预测在行加权下读作"duration 比预测 0 好 8.4%"，作品等权后只有 3.8% 且区间跨零。以后一律以作品等权 + 区间为准，单点行加权 MAE 不得用于收益主张。
3. `predict_recording_median` 之所以强，是因为"整条录音整体偏长/偏短"本身就解释了大量误差，而模型连这个常数级偏置都没学到——与 ICC 那轮"duration 水平里约 1/3 是谱面属性"正好对上。这给出一条尚未验证、但与门槛直接挂钩的建模方向：显式预测"每条录音的整体偏移"再叠加曲内形状（两部分模型），而不是让一个头去兼顾两者。它需要先解决"推理时该偏移从哪来"（谱面特征可预测的那 1/3 由模型学，其余必须保留规则回退），因此属于新一轮设计，不是重训。

## 2026-10-11 A-lite：不重建分片的形状特征，中性偏负

`midi_features.py` 写的是 `pitch_centered = (pitch − 60) / 24`、第 3 列原样存 `score_onset_beats`、第 4 列 `log1p(duration_beats)`，音高是整数且网格远粗于 float32 精度，所以**音高与时值可从已建分片无损反解**——补特征不必先重建 1238 个 npz。`training/shape_features.py` 据此在加载期派生三列纯谱面几何特征（同音高前/后击键距离、本音符记谱结束瞬间仍在响的其它声部数），只读 `note_features`、不读目标列。

过程中修掉两个真问题，都值得记住。第一，`expm1(float32(log1p(2)))` 的 ~4e-9 拍往返误差会把"恰好在下一音符开始时结束"（键盘音乐的绝大多数情况）判成重叠；修法是 `searchsorted(..., side="right")` 给出正确的"≤"语义，再用 `BEAT_TOLERANCE = 1e-6` 拍解并列，并按实测校准：50 条验证录音中最小的不同起点间隔为 **0.0208 拍，是容差的约 2.08 万倍**，因此容差只吸收存储噪声、不会合并真实事件。第二，评估工具原先用默认 17 列加载样本，评 20 列的形状臂时直接广播报错（`shapes (235,17) (20,)`）；现在 `checkpoint_preparation_flags()` 把"该 checkpoint 用了哪些输入/目标变换"从 run_config 读回来，audit 与两个评估工具统一按它分组加载。

臂的结果（`--shape-features`，15 epoch × 3 seed，其余超参与 fixed 臂逐字相同；宽度 17→20、参数 52,872→53,064；产物 `v4/shape_features_20261011/shape_seed*`；分解报告 sha256 `290e52f3d397d3e7dab95c9aac3f5fe722857a1cc6e0560cedd3835f391a3b32`，bootstrap sha256 `abfe35baa47ee650b18dad5720d4aef24457c77556cc11923974358ee9b4f026`）：duration `shape_mae` 0.5047 对 0.5069（Δ −0.0022，落在 seed 跨度 0.0032/0.0065 内），`raw_mae` 0.6039 对 0.6106（−1.1%），ioi 略差、onset 几乎不变；作品等权 bootstrap 仍判未过门槛（duration vs predict-zero −0.0225，CI [−0.0731, +0.0299] 跨零；onset 仍显著差于原谱 +9.51 ms，CI [+2.66, +17.50]）。**"形状缺口来自输入缺少声部连续性"这一假设没有被这三列支持。** 由于 ρ_shape=0.657 表明这块缺口原则上可被谱面解释，继续追就得换解释变量（记谱的articulation/踏板标记、短语边界、局部速度上下文）或转向两部分建模，而不是再堆同类几何列——每加一列都要付"旧 checkpoint 作废 + 重训基线 + 重跑 bootstrap"的代价。
