# 演奏增强模型：接入距离评估（2026-10-11）

回答一个问题：**按现在的证据，这个模型什么时候能正式接进软件里用。** 结论先给，再给可核对的数字和判定条件。

## 结论

现在不能接入，也**无法给出日历时间**。可辩护的说法只有一句：**在任何一条通道于其绑定门禁上拿到区间支持的改善之前，接入工程不该开工**；而当前三条通道全部为负，duration 比最强简单基线还差约 17.9%。

更关键的是：接入不是一个门槛，是四层，而且**最外面那层从来没被测量过**。把"还要多久"拆开看才是可决策的。

同日的两次续做把这份判断收紧了：`rules` 基线补进来之后发现**它自己比照原谱弹还差**（duration 0.797 对 0.576），所以"胜过 rules"不构成理由，真正的对手是 `identity`；而试图用重标定常数去走不依赖模型的捷径（路径 B 的第一步）**已经试过并失败了**，失败原因指向规则形式而非数值（见"路径 B"小节）。剩下的可辩护立场是：**duration 需要的是逐音符时值的表达能力，而不是第 N 组常数或第 N 次重训。**

- `human_preference_required_for_default_enable: true`，且 velocity/pedal/micro 三路当前禁用；
- 阈值来源被自己标注为"项目工程目标，不是行业标准"。

状态：**未通过**。2026-10-03 的首次 pilot 六条候选序列全部失败（见 `docs/2026-10-03_累计节奏与演奏接入门禁实施记录.md`），而该 pilot 消费的正是序列 checkpoint（`run_playback_adoption_pilot.py` 导入 `train_sequence_expression`、`audit_sequence_expression`），所以"跑不了"不是借口。

`rules` 基线已在同日补进作品级 bootstrap（见下节"rules 基线实测"），所以口径缺口已闭上：结论仍然不变，而且比原来更强——**模型在 duration 上比现行规则好 30%，但比"照原谱弹"只好 3.8%，而 ioi 与 onset 比原谱更差**。

### 第 4 层：接入工程本身（0%，且当前构建根本跑不了模型）

即使第 1、2 层明天变绿，代码里还缺：

- **没有导出与运行时**：全仓 `core/gui/store/main.py` 对 `onnx|InferenceSession|planner_.*` **零命中**；训练只写 `checkpoint_best.pt`；`AutoMusicPlayer.spec` 连 `numpy` 都排除在打包之外。E 盘那批 `planner_*.onnx` 是冒烟产物，仓库里没有任何地方引用。
- **没有调用点**：现有表现力全部来自规则路径 `core/humanize.py` 的 `HumanizeParams`（jitter/breath/hold 分层/leap/min_gap/correlation），由 `gui/player_tab.py` 的 `build_event_plan` → `core/compiler.py` 消费；配置只在 `config.yaml` 的 `player.humanize`，**没有 GUI 开关**。安卓侧同理，只带移植的 `Humanize.kt`。
- **没有针对模型输出的护栏契约**：现有的夹取是编译链自带的（`max(t, prev_kb_up + min_gap_ms)`、`MAX_HOLD`、60 ms 最小可弹时值 `MIN_GAME_NOTE_MS`），但模型 delta 没有自己的夹取、时值累计漂移上限或独立 feature flag——因为它连调用点都没有。回退目前只有"humanize 总开关关掉"这一档，粒度不足以做"按作品/按来源回退"。

## rules 基线实测（同日续做，`training/rules_baseline.py`）

做法：直接调用 app 在用的 `core.humanize.build_plan`（默认参数，与 `config.yaml` 的 `player.humanize` 逐字相同：jitter 12 ms、breath 25 ms、相关系数 0.65），把它产出的 `(offset_ms, hold_ratio)` 经过 `core/compiler.py` 的链式防叠键下限，再投到标签单位：onset 用净偏移毫秒、ioi 用 `log(施加后间隔/谱面间隔)`、duration 用 `log(hold × element 占用时长/记谱时值)`。全程只用锁定的谱面时间轴（`fixed_score`，本语料参考拍长 0.5 s/拍），不读任何演奏侧信息。每条录音跑 8 次独立会话，报两种口径：`rules_session`（会话间平均绝对误差，等于"一次真实播放"）与 `rules_centred`（先平均预测再算误差，按 Jensen 必然更强）。50 首、2000 次重抽、作品等权，与模型同一套配对。

结果（作品等权 MAE，标签单位；`shape6` 臂与 `fixed` 臂几乎一样，只在 duration 上差 0.002）：

| 通道 | 模型 | identity（=predict_zero） | rules | 模型 vs rules | 模型 vs identity | 区间 |
|---|---|---|---|---|---|---|
| duration | 0.5545 | 0.5763 | 0.7973 | **+30.4%** | **+3.8%** | vs rules 支持（CI [−0.301,−0.186]，P(更差)=0.000）；vs identity **不支持**（CI [−0.069,+0.026]） |
| ioi | 0.1576 | 0.1573 | 0.1639 | +3.9% | −0.2% | 都不支持 |
| onset | 548.84 ms | 540.81 ms | 904.45 ms | +39.3% | **−1.5%** | vs rules 不支持（CI [−910,+11]）；vs identity **显著更差**（CI [+0.15,+15.74]，P(更差)=0.976） |

四条必须一起读的结论：

1. **现行规则在钢琴材料上比"照原谱弹"更差**（duration 0.797 对 0.576）。原因可量化：hold 三档的中位数在 0.70–0.85（log ≈ −0.26），而本语料的真实/记谱中位是 0.922（log ≈ −0.082），且记谱时值基本就等于到下一 onsets 的间隙（`gap/written` 中位 1.000、q10 0.500）——规则是为 21 键旋律调的，套到钢琴上会把音切得过短。所以**"打得过 rules"在这批数据上不构成价值证据，真正该打的基线是 identity**。
2. 由此暴露一个策略风险：POLICY 的 `required_baselines` 把 identity / rules / zero_model_adapter 并列，若实现按"胜过其中任一"判定，它会被一个比原谱还差的基线轻易满足。建议（需你拍板）把门禁写死为**必须胜过 identity 且作品级区间支持，rules 只作非劣检查**。
3. **表示陷阱**：第一版投影把"记谱时值"当作 app 的 element 时长，于是每个元素的释放都越过下一 onset，链式防叠键沿乐曲滚雪球，rules 的 onset 误差被推到 **约 21.8 秒**——那份产物（`rules_baseline_probe_20261011/*`）已作废，只留作反面教材。app 的 element `dur` 语义是"到下一个事件之前占用的时间"，投影必须用它；改正后三个通道的"无法 emitted 行"均为 0。
4. 大跳进换指这条规则在这批数据上**一次都不会触发**：`_pitch_value` 只认 `low/mid/high + 1..7` 的级名，MIDI 音高不可解析。按半音代理口径统计，63,947 个相邻对里有 31,153 对（48.7%）本该触发。要用它，先决定音高命名；不用它，就承认现行规则在钢琴上少了一条塑形。

## 所以"什么时候"——按条件给三条路径

**路径 A：模型接入（当前主线）。** 关键路径不是算力，是监督形式。已证伪清单：窗口布局、bar 辅助 loss、loss 权重、目标重参数化、14.2 倍容量、A-lite 三列弱几何、6 列强几何（后者在离线 ridge 上确有 +52.8%/+37.8% 出折增量，进 GRU 后 +0.40% 反向）。剩下唯一没被证伪的方向是**别再逐点回归单条含噪录音**：以"曲内共享形状剖面"为监督目标（或显式两部分：录音级水平 + 曲内形状）。这一轮的实验成本很小（实测三 seed 训练 3.5 分钟 + 评估 3 分钟），所以它能在**一天内给出是/否**；但按历史基率，不该假设一次就过。若这一轮也失败，按纪律应当**关闭模型接入线**，而不是再换一种调参。

**路径 B：不经过深度模型的接入（已按最便宜的形态做过，2026-10-11 负向）。** 原设想是把 `duration_versus_local_mean_log` 这类已被量过的谱面关系写成规则，或至少**按本语料重标 `core/humanize` 的三档 hold**。这件事已经做完：`tools/fit_humanize_hold_bands.py` 只在 train 划分（444,063 条有监督音符）上取"每条音符要求的 hold = exp(label) × written / span"的档位中位数，拟出 `short 0.980 / mid 0.915 / long 0.849`，再用同一份投影和同一套作品级 paired bootstrap 评分。结果在验证集上**比 identity 更差**：duration −15.0%、ioi −9.2%、onset −258.8%（CI [+168,+3085] ms），虽然比现行 rules 好 16.9%。产物 `hold_band_refit_20261011`，sha256 `a7c076df…`；`config.yaml` 与 `core/humanize.py` 全程未改，没有任何应用行为被触碰。

三条诊断决定了后续判断：**其一**，失败原因是**规则形式而不是常数值**——hold 接近 1.0 会抽掉释放余量，链式防叠键转为主导，7,228 和弦的密集段落里平均每步约 +1.5 ms 把起音平均偏移从 +94 ms 推到 **+3,418 ms**；app 的计时锚定本就依赖 `hold < 1`。**其二**，同一数据里 **32.6%–62% 的音符要求 hold > 1.0**（复调延音跨过下一 onset），"一元素一 hold"在结构上无法表达，只能在 1.0 截断。**其三**，因此"现行规则比照原谱还差"不是没调好，而是不适配钢琴材料；**模型比 rules 好 30% 反映的是基线弱，不是模型强**。

要在规则路线上继续，唯一有依据的方向是**逐音符独立时值**的表达（对 `core/humanize.py` / `core/compiler.py` 的功能扩展，属接入工程改动，需要立项），而不是再标定一组常数。

**路径 C：接入工程提前做（不推荐现在做）。** 唯一例外是为了路径 B 需要的基础设施（把候选时值计划送进 `build_event_plan` 的影子对比、按作品回退的 flag）。若走 B，这些是顺带产出；若只为模型预建 ONNX 运行时，是在给一个未过门禁的模型修路。

## 不该再做的事

把行加权读数当成果（同批预测在行加权下"duration 比预测 0 好 8.4%"，作品等权后缩到 3.8% 且跨零）；在门槛未过时启动真人 A/B；再加一列几何特征或再加大模型；把 `codex/expression-research` 推到公开远端；在没 rebase 的情况下把它合进 main（会删掉 12 个安卓文件）；以及**把"胜过 rules"当成接入理由**——在这批语料上 rules 比照原谱弹还差 38%（duration 0.797 对 0.576）。

## 一句话回答

**"什么时候能正式接入"目前的答案是：不是时间问题，是证据问题，而且差距已经能量化。** 在 POLICY 自己的基线口径下，最好的通道 duration 比 identity 只改善 **3.8%**（需要 10%，区间还跨零），ioi 与 onset 比 identity **更差**（onset 显著更差，+8.0 ms，CI [+0.15,+15.74]）。不依赖模型的那条捷径也试过了：按语料重标 hold 之后比 identity 还差 15%，原因是"一元素一 hold"这个形式表达不了复调延音（32.6%–62% 的音符要求 hold > 1.0），而不是常数没调好。所以剩下的只有两个可辩护选项：**给 duration 换成逐音符时值的表达能力**（要立项，改的是 `core/humanize.py` / `core/compiler.py`，不是模型），或者**关掉增强线、把工程精力放到门禁其余环节**。在那之前，接入工程一行都不该开工，真人 A/B 也不该启动。
