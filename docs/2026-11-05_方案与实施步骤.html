01旧曲库是否保留

已核实代码，非推测。结论：曲库跟着 data/ 目录走，替换 EXE 不影响。

现状机制

数据目录由 main.py:180 的 _resolve_data_dir 决定：便携版用 exe 旁 data/，安装版落到 %LOCALAPPDATA%\AutoMusicPlayer\data，MSIX 走 LocalState 并先做一次只复制不删除的合并。曲库本体在 core/database.py：SCHEMA_VERSION = 2，升级前先用 SQLite backup API 生成 scores.db.pre-v2.<时间戳>.bak；表结构全部 CREATE TABLE IF NOT EXISTS，只增不改。来源附件按 SHA-256 存在 data/sources/。

真实风险

编号风险触发条件后果
R1整包覆盖解压发布包内含 config.yaml 与空 data/旧 scores.db 被冲掉或指向空目录
R2data_mode 变更便携版与安装版互切库还在但看不见，表现为「乐谱全没了」
R3schema 版本兼容清单要求更高数据库格式或客户端过旧下载前拒绝并提示备份后手动升级，当前程序也拒绝打开未来格式
R4迁移备份位置首次 schema 升级状态栏和曲库页显示备份路径

已有资产：曲库找回

core/library_recovery.py 已经是完整实现：只读打开旧库、校验 user_version、导入前备份当前库、按内容指纹去重可重试、附件必须落在旧库 sources/ 内且 SHA-256 一致、失败整体回滚。界面入口是乐谱库页的「找回旧曲库」按钮。

02自动更新的现状与缺口

验签下载链路完整，问题在发布侧一致性。

core/update_checker.py 已具备：Ed25519 验签（canonical JSON）、双镜像取最高有效序列、拒绝回滚、签发/过期时间校验、强制 HTTPS、清单 1 MB 上限、更新包 2 GB 上限、边下边算 SHA-256、临时文件校验通过后才原子改名且绝不覆盖同名文件、可取消并上报进度。

本地完成，线上待同步。程序和本地清单均为 1.5.1 / sequence 151。重签后模拟 1.5.0 客户端可发现新版，1.5.1 判断为最新。GitHub/Gitee 正式镜像清单需要按文件清单确认流程发布。

自替换没有实现，是刻意为之：docs/发布签名与更新器门禁.md 要求正式 Authenticode 证书与回滚测试证据齐备后才进入第二阶段。当前本机有 signtool，但没有可正式发布的证书，因此保持「下载并提示手动替换」。

P0-1启动时探测旧库并询问

目标 scores.db 不存在、但另一侧存在旧库时，弹一次「发现旧曲库」；用户确认后复用 recover_library()。不自动改配置、不自动迁移、原库只读。

已验证。已知另一侧旧库可被发现，拒绝后旧库字节相同，确认后界面刷新出旧谱。

P0-2用 db_schema_version 做发布门禁

在 download_update() 联网前判断 manifest.db_schema_version > ScoreDB.SCHEMA_VERSION 即拒绝，提示手动更新；min_supported 不满足时给出警告。

已验证。签名清单要求 schema 99 或更高最低客户端版本时，下载联网前被拒，保存目录为空。

P0-3版本三处同步，缺一拒发

version.txt → core/version.py → updates/stable.json 三者必须一致，由发布脚本比对，不一致就终止打包；清单随后用 tools/update_manifest.py sign 重签。

已验证。spec 在 Analysis 前执行版本检查，单独更改 version.txt 或清单序列号都会失败。最终文件的哈希在构建后由 release_check 校验。
